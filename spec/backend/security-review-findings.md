## Medium

- [x] **`member-photos` bucket is fully public with no auth check, and object paths are
  predictable.**
  Object keys are `{memberId}/original-{timestamp}.jpg` / `{memberId}/thumbnail-{timestamp}.jpg`
  ([member.service.ts:214-224](../../frontend/src/services/member.service.ts#L214-L224)) —
  sequential bigint member IDs, trivially enumerable — but that stopped being exploitable
  once the fix below landed: the bucket now requires an active session to read at all.
  **Fixed** ([20260723000000_member_photos_private_bucket.sql](../../supabase/migrations/20260723000000_member_photos_private_bucket.sql)):
  bucket flipped to `public = false`; `member_photos_read_public` replaced with
  `member_photos_read_active_users`, gated by `is_active_user()` — the same access level
  every other member field already has. Reads now go through short-lived signed URLs,
  generated by a new shared helper
  ([photo-urls.ts](../../frontend/src/lib/photo-urls.ts)) called from
  `memberListRepository.getAll()` and `memberRepository.getById()` right after fetching
  rows — `members.photo_url`/`photo_thumbnail_url` switched meaning from "a public URL"
  to "a `member-photos`-relative storage path" (a signed URL itself can't be persisted,
  it expires), with a one-time backfill regex converting any previously-stored public
  URLs. No changes needed to `MembersListPage.tsx`/`MemberDetailPage.tsx`/
  `PhotoLightbox.tsx` — they still just render whatever string they're given.

  bucket row: `file_size_limit = 5242880` (5 MiB), `allowed_mime_types =
  array['image/jpeg', 'image/png', 'image/webp']`.
- [ ] `weight_kg`/`height_cm` are unscoped `numeric` (arbitrary precision) while every

  `database.md` gets a numeric-precision pass anyway.

## Already solid (no action needed)

- Seed/schema separation: reference data (`branches`, `plans`, `configuration`) lives inside
  the master-data migration under an explicit "Seed Data" section with idempotent
  `ON CONFLICT`; throwaway dev fixtures live only in `seed.sql`, wired through
  `config.toml`'s `db.seed.sql_paths` so it never runs against a pushed/production project.
- `20260721000000_member_list_view_photo_url.sql` appends the new column at the end of the
  view's select list rather than inserting it near `photo_thumbnail_url` — correct, since
  `CREATE OR REPLACE VIEW` can't reorder or insert output columns (SQLSTATE 42P16) — and the
  migration explains why.
- RPC functions backing `create-subscription`/`update-subscription` are correctly
  `REVOKE`d from `PUBLIC` and `GRANT`ed only to `service_role`.
- Every Edge Function (`invite-user`, `list-users`, `update-user`, `delete-branch`,
  `delete-plan`, `create-subscription`, `update-subscription`) follows the same
  caller-auth → profile-lookup → admin/active-check → validate → act shape consistently —
  no divergent patterns between them.
