# Database Schema & CRUD-Flow Review

> Two-part audit done 2026-07-27, at explicit request: (1) every table in `supabase/migrations/` checked for required fields, validation constraints, audit-trigger attachment, and soft-delete/hard-delete-prevention; (2) every page in the app traced end-to-end — Create/Retrieve/Edit/Delete — to confirm each UI action hits the right table/columns, with no field silently dropped from an update payload or left stale in the UI after a save. The second part was specifically hunting for a bug class already found once in this codebase: `update_subscription_header` used to unconditionally overwrite `notes` even when a caller's payload omitted it (fixed in `20260725000000_update_subscription_header_notes_fix.sql`, see [audit-findings.md](./audit-findings.md)).
>
> Checklist for tracking — check items off as they're addressed, same convention as [domain-model-review.md](./backend/domain-model-review.md) and [audit-findings.md](./audit-findings.md).
>
> **Headline:** one critical, previously-undetected bug — `audit_row_changes()`'s INSERT branch would have broken every role grant in the app (inviting a user, editing a user's roles, the documented bootstrap-admin step) the first time any of them actually ran, because it tried to log a column `user_roles` doesn't have into a `NOT NULL` field. Fixed below. Everything else found across ~30 traced CRUD flows and 11 tables was minor: three client-only "required" validations with no DB-level backstop, a couple of narrow/low-severity races, some stale doc sections, and one real (now-fixed) non-atomic multi-row write. No other instance of the "field silently dropped from an update" bug class was found anywhere — every other update path in the app either sends the complete object every time or correctly uses `coalesce` against omission.

## Critical

- [x] **`audit_row_changes()` broke every `user_roles` INSERT — i.e. every role grant, app-wide.** `20260722000000_roles_and_user_roles.sql`'s INSERT branch computed `v_record_id := v_new ->> 'id'` with no fallback. Correct for every other audited table (all have a real `id` column) — but `user_roles` has none (its key is `(user_id, role_id)`). This resolved to `NULL`, and since `audit_log.record_id` is `text not null`, the resulting `insert into audit_log` inside the trigger raised a NOT-NULL violation, aborting the whole enclosing transaction. `trg_user_roles_audit_fields` fires `after insert or delete` on `user_roles`, so this hit **every** `insert into user_roles` — `replace_user_roles()` (used by both `invite-user` and `update-user` for any role assignment) and the manually-documented bootstrap-first-admin step. The DELETE branch already had the correct fix (`coalesce(v_old ->> 'id', (v_old ->> 'user_id') || ':' || (v_old ->> 'role_id'))`, same file line 150) — it was simply never mirrored into the INSERT branch (or the dead-for-`user_roles` UPDATE branch).
  **Fixed** ([20260728000000_fix_audit_row_changes_user_roles_insert.sql](../supabase/migrations/20260728000000_fix_audit_row_changes_user_roles_insert.sql)): `create or replace function audit_row_changes()` with the same `coalesce` fallback applied to the INSERT and UPDATE branches too. Safe for every other table — they all have a real `id` column, so `v_new ->> 'id'` already resolves correctly and the fallback is simply never reached for them. Verified by reading the actual function body directly (not just trusting the audit's summary) before writing the fix.

## Medium

- [x] **Member Numbering's Global Settings save wasn't atomic.** `memberNumberingRepository.updateConfig` ran three independent `.update()` calls (via `Promise.all`) against the three `configuration` rows — three separate statements, not one transaction. If the 2nd succeeded and the 3rd then failed (a transient network blip mid-batch), two of three keys were durably changed in the DB, but the page's catch block only set an error banner and never reloaded — the form kept showing the old pre-submit draft while `generate_member_number()` was already reading a mixed old/new state. Same *symptom* as the hunted bug class (DB state silently diverges from what the UI shows), via a different mechanism (non-atomic multi-row write, not an unconditional overwrite).
  **Fixed:** new RPC `update_member_number_config(p_start_sequence, p_increment, p_padding_width)` ([20260729000000_member_number_config_atomic_update.sql](../supabase/migrations/20260729000000_member_number_config_atomic_update.sql)) updates all three rows in one statement/transaction — `security invoker`, so each `UPDATE` inside it still runs as the calling admin and is individually gated by the existing `configuration_update_admin` RLS policy, same protection as before, just atomic now. `memberNumberingRepository.updateConfig` (`frontend/src/repositories/member-numbering.repository.ts`) now calls this RPC instead of three separate updates. Also added a defensive `loadAll()` reconciliation call in `MemberNumberingPage.tsx`'s error handler, in case a response is lost after a server-side commit that did succeed. Documented in [member-management.md §3.1](./backend/member-management.md#31-admin-configuration-member-numbering-screen).

- [x] **`database.md`'s own Storage section was stale**, independently of the (already-fixed) staleness in `member-management.md §8`. Still documented the `member-photos` bucket as `public = true` with a `member_photos_read_public` policy — the actual schema (`20260723000000_member_photos_private_bucket.sql`) made it private with `is_active_user()`-gated reads months before this line was corrected. A reader auditing from `database.md` alone would have believed photos were still publicly readable.
  **Fixed:** rewrote the section to match the actual private-bucket/signed-URL design and explain why it changed, cross-referencing `member-management.md §8`.

## Low / polish

- [ ] **`name`/`code` "required" validation is client-side only on Plans, Branches, and Roles** — the DB column is `not null` but has no CHECK rejecting an empty/whitespace string, so a forged direct API call could insert `name: ""`. Same shape as an already-accepted-as-known gap elsewhere in this codebase; not fixed here, just newly confirmed across all three catalog tables. Low priority given these are all admin-only, RLS-gated writes, not public-facing input.
- [ ] **TOCTOU race on the indefinite-plan duplicate check in `create-subscription`.** The "member already has this indefinite plan" check (REQ-SUB-007) runs as a separate `SELECT` before the RPC call, outside the RPC's atomic transaction. Two concurrent checkouts for the same member+indefinite-plan could both pass the check before either inserts, producing two indefinite items for the same plan/member. Narrow window (same admin action, split-second timing), undocumented as an accepted trade-off (unlike the equivalent, explicitly-documented race in `delete-plan`/`delete-branch`'s count-then-update shape).
- [ ] **`update-subscription`'s `payment_mode` validation has a dead-but-real gap.** `if (payload.payment_mode && !['Cash','UPI','Card'].includes(...))` skips validation entirely for an explicit empty string, which would then flow through `coalesce('', payment_mode)` and attempt to write `''` into a CHECK-constrained column, surfacing as a raw 500 instead of a clean 400. Not reachable through the actual UI (the chip selector never produces an empty string) — dead code path today, but a real gap if a future caller ever sends one.
- [ ] **Deactivated staff show as "Unknown" for `created_by`/`handled_by_staff`.** Both are resolved to display names via `profileRepository.getAllActive()`, which filters `is_active = true` — correct underlying data, misleading display once the referenced staffer is deactivated. The edit-mode `handled_by_staff` `<select>` has the same restriction: if the current value points at a now-deactivated staffer, the controlled select has no matching `<option>` and renders blank during edit — but since `onChange` only fires on explicit interaction, an unmodified save still round-trips the original value correctly (verified, not a data-loss bug — display-only).
- [ ] **Orphaned storage blob on partial photo-upload failure.** `memberService`'s photo upload does both the original and thumbnail uploads via `Promise.all`, then a single `UPDATE` setting both URL columns together — genuinely atomic at the DB level (no half-set row), but if one of the two storage uploads succeeds and the other fails, the successfully-uploaded blob is never referenced by any column and never cleaned up. A storage leak, not a data-correctness bug.
- [ ] **Audit Log's date-range filter uses UTC day boundaries, not local time.** `${startDate}T00:00:00.000Z`/`${endDate}T23:59:59.999Z` — for a non-UTC admin, entries near midnight can appear to be filed under the "wrong" day relative to what the date picker implies. Cosmetic; the filter itself is applied correctly, just with a UTC seam.
- [ ] **Several admin-only UPDATE RLS policies don't exclude soft-deleted rows.** `branches_update_admin`, `plans_update_admin`, `roles_update_admin`, `members_update_active_users`, and the two `profiles` update policies all gate on `is_active_user()`/`is_active_admin()` but never `deleted_at is null` — a client that retains a soft-deleted row's id could still write to it via a direct API call (the UI itself never offers this path, since deleted rows are excluded from every list query). Matches `database.md`'s documented design exactly (not a doc/code disagreement) but arguably sits in tension with this project's stated "soft-deleted rows are invisible to normal reads" principle, which is silent on writes. Flagging as a product decision to make explicitly, not a bug to reflexively fix — a soft-deleted row is a dead end from every UI path already, so the practical exposure is a forged/scripted API call, not anything reachable by a staff member clicking around.
- [x] **`domain-model.md`'s Member table didn't document the `weight_kg`/`height_cm` CHECK bounds** (`between 1 and 500` / `between 1 and 300`) even though `database.md` and the actual migration both enforce them.
  **Fixed:** added the CHECK descriptions to the field table.

## Already solid (no action needed)

**Schema, table by table** — every one of `profiles`, `roles`, `branches`, `plans`, `configuration`, `members`, `member_number_sequences`, `subscriptions`, `subscription_items`, `audit_log` passed on: required fields matching the domain model, validation CHECK constraints present and logically correct (not inverted, not off-by-one — spot-checked the actual expressions, not just the comments describing them), `set_audit_fields()`/`prevent_hard_delete()`/`audit_row_changes()` triggers attached everywhere they should be (and correctly *not* attached to the documented-exempt internal tables), RLS enabled with policies matching the intended access model, FK-referencing indexes present (including the batch added in `20260724000000`), and no unexpected `ON DELETE CASCADE` anywhere in the schema (`subscription_items.plan_id`'s `ON DELETE RESTRICT` remains the one deliberate explicit case). `member_number_sequences`'s branch-only (not branch+year) key was independently re-verified against the trigger body, not just trusted from its own migration's comments.

**CRUD flows, page by page** — traced Create/Retrieve/Edit/Delete on Member Management (Add/Detail/List), Subscription Management (checkout creation, history retrieve/edit, Reports), and every admin catalog screen (Plans/Branches/Roles/Users/Invite/Audit Log/Member Numbering). In every flow: every field the UI collects reaches the actual insert/update payload (no silent drops); every field the UI renders is present in the corresponding select; every delete goes through its guarded Edge Function, never a direct table write; every list correctly re-fetches after a mutation (no stale rows); the already-fixed `notes` bug is verified correctly wired end-to-end from the UI through the Edge Function into the RPC, including the exact "field omitted vs. explicitly cleared to null" distinction; role reassignment sends the complete new role set (a true replace via `delete` + bulk `insert`), never a partial diff that could silently drop a role; the last-active-admin lockout is enforced both client-side (disabled controls) and server-side (would reject if bypassed).
